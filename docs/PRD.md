# 通用 ChatBI 平台：电商 Mock 场景 PRD

- 版本：0.3（P2 评审稿）
- 状态：项目方已于 2026-11-06 批准（v0.3）
- 日期：2026-11-06
- 本 PRD 覆盖：首个电商 Mock 场景及平台 MVP 的产品要求。
- 依据：P1 竞品调研、项目方确认的电商首期定位，以及 P2 对 UQ-01 至 UQ-10 首版范围的决定。

## 1. 产品简介

### 1.1 产品目的

建设一个通用类型的 ChatBI 平台，帮助业务人员通过自然语言查询数据并理解结果。首期使用电商 Mock 数据做出可演示、可核对的问数体验，后续逐步扩展通用语义配置、更多数据主题、模型接入和云端部署能力。

所有阶段只使用虚构的 Mock 数据：早期在本地存储，后续迁移至云数据库。不得接入真实业务数据或真实个人信息。

### 1.2 产品设计重点

以下三项已由项目方确认：

1. **答案可核对**：结果能对应到实际查询结果和 Mock 数据。
2. **口径清楚**：说明使用的指标定义、时间范围、维度和筛选条件。
3. **过程可检查**：用户能看到系统如何理解问题；遇到关键歧义时先确认或澄清。

大模型用于辅助理解自然语言和形成查询计划。业务指标定义、权限和查询执行由平台控制；模型不得自行编造指标口径或绕过服务端校验。

## 2. 用户与使用场景

P1 用户类型和痛点来自市场资料归纳，是产品设计假设，不是用户访谈结论。

| 角色 | 主要任务 | 关注点 |
|---|---|---|
| 电商运营人员 | 查看销售、订单、商品/类目、渠道和时间变化 | 快速得到答案，能核对口径与筛选 |
| 业务负责人/管理者 | 查看整体表现和重点变化 | 结论易读，有证据，不把相关性说成因果 |
| 项目验收者/数据维护者 | 核对 Mock 数据、指标定义、问数解析和执行结果 | 可重复、可追踪，能定位错误环节 |

核心流程：用户提问 → 系统解析指标/维度/筛选/时间 → 必要时澄清或确认 → 服务端校验 → 执行 Mock 数据查询 → 展示数字/表格/图表及口径依据 → 用户可继续追问或修正。

## 3. 产品目标与非目标

### 3.1 目标

- 让用户用自然语言查询电商 Mock 数据，不需要自行编写 SQL。
- 对明确问题返回正确、可复核的结果；结果形式与问题匹配。
- 对缺少条件、概念歧义或超出支持范围的问题，澄清或拒答，不猜测答案。
- 支持用语义词典管理字段、指标、维度、业务术语、别名及关系，为大模型问数提供受控业务上下文。
- 通过标准问题集持续验证不同阶段的问数理解和结果正确性。
- 保持存储实现可替换，使本地 Mock 数据可迁移到云数据库。

### 3.2 非目标

- 接入真实电商平台、生产数据库、真实客户数据或真实个人信息。
- 首期支持任意行业、任意数据源的即插即用配置或完整多租户管理。
- 让大模型直接执行任意 SQL、写入或删除数据。
- 首期提供完整的语义词典可视化管理后台；初版可使用受版本控制的配置文件/数据。
- 无可靠数据支持的因果归因、预测、自动预警或自动执行经营动作。
- 将通用闲聊、文档问答或 RAG 知识助手作为首期问数主流程。

## 5. 功能需求

优先级含义：**Must** 为首版必要；**Should** 为建议纳入；**Could** 为可选。项目方已确认下表优先级分组，并于 2026-11-06 批准 PRD v0.3。

| ID | 已确认优先级 | 功能需求 | 验收要点 |
|---|---|---|---|
| FR-001 | Must | 仅从固定 Mock 数据集提供答案，并在页面/结果标识 Mock | 数据生成、重置和版本可识别；全流程没有真实业务数据来源 |
| FR-002 | Must | 接受用户自然语言问数，并给出明确的处理中、成功或失败状态 | 有效问题可提交；空输入不查询；重复提交行为明确 |
| FR-003 | Must | 将问题解析为结构化意图：指标、维度、时间范围、筛选、排序/数量和粒度 | 结果附带可读的理解摘要；解析不全不得静默猜测 |
| FR-004 | Must | 对缺少必要条件或存在会改变结果的歧义进行澄清/确认 | 澄清前不执行有歧义查询；用户补充后以最终条件查询 |
| FR-005 | Must | 查询只使用语义目录中已定义的数据、指标、维度和关系 | 未知字段/指标或不兼容粒度被拒绝或澄清 |
| FR-006 | Must | 服务端执行权限和查询安全校验，只允许受控只读查询 | 拒绝写操作、危险表达、超范围和未授权查询；具体限额在 SDD 定义 |
| FR-007 | Must | 根据答案类型展示数值、表格或适当图表 | 展示内容与查询结果一致；无数据有明确空状态 |
| FR-008 | Must | 展示答案口径与条件 | 包含指标解释、时间范围、关键筛选/分组条件和 Mock 标记 |
| FR-009 | Must | 对不支持、未知术语、无法消歧、无权限、无结果、超时和系统失败给出明确反馈 | 不生成伪造数值；不向终端用户泄露内部堆栈或密钥 |
| FR-010 | Must | 支持边界明确的同会话追问 | 只继承上一轮明确的指标和时间范围；允许补充/调整一个维度；每轮展示解析结果和查询条件并重新校验；不支持跨主题、信息省略推断或复杂分析链 |
| FR-011 | Should | 提供与当前数据/语义范围匹配的推荐问题 | 推荐问题可被当前版本执行，不引导到未支持能力 |
| FR-012 | Should | 提供答案反馈并区分理解、指标口径、筛选、查询结果、图表等问题 | 反馈可记录并关联到对应问题/评估条目 |
| FR-013 | Must | 在验收/调试视图展示结构化查询计划或安全后的 SQL | 便于核对是否查询正确；普通用户界面不显示 SQL；禁止执行未经校验的模型 SQL |
| FR-014 | Must（后续阶段） | 支持后续接入大模型辅助问数 | 首版不调用大模型理解问题；后续通过后端适配层调用，模型只能提出结构化意图/计划，服务端校验后才能执行 |
| FR-015 | Must（平台路线） | 本地 Mock 存储与未来云数据库通过存储适配边界解耦 | 迁移云数据库时问数业务规则和语义定义不与具体存储实现耦合 |

## 6. 业务规则与答案约束

1. 指标公式、时间口径、退款处理、聚合粒度和同义词以版本化语义目录为准。
2. 模型只负责辅助理解和组织表达；数字必须来自受控查询结果，说明文字不得改写数值或口径。
3. “为什么”类问题只能依据可计算、可展示的数据分解给出有限解释；不得把相关性描述成已证明的因果关系。
4. “最近 N 天”“昨天”“本月”“本周”按 `Asia/Shanghai`（北京时间）的固定时区和完整自然日解释；P3 将具体边界示例写入语义定义和黄金集。
5. 发生指标歧义时优先澄清；若词典明确设定别名/同义词，则按已登记映射处理并在答案中显示规范指标名。
6. 所有回答应清楚标明这是 Mock 数据结果，不代表真实经营数据。
7. 当前确定性指标包括销售额、订单数、客单价和 UQ-07 商品退款订单率；金额退款率仍未纳入。
8. 首版图表：单个数值用指标卡；按日期变化用折线图；按商品、类目或渠道比较用排序表格和柱状图。

## 7. 异常与状态要求

| 状态 | 系统行为 | 用户可采取的动作 |
|---|---|---|
| 空输入 | 阻止提交并提示输入问题 | 输入问题 |
| 正在理解/查询 | 显示当前处理状态，防止重复提交；首版查询不可取消 | 等待查询完成；完成或报错后可继续提问 |
| 需要澄清 | 说明缺少/有歧义的条件，并提供清晰选项或补充输入 | 选择或补充条件 |
| 不支持 | 说明当前支持的分析范围，可给出候选问题 | 修改为支持的问题 |
| 未知指标/术语 | 不猜测；说明未识别的词，并提示当前可用指标/术语 | 选择已提供的规范术语重新提问 |
| 无权限/不允许查询 | 拒绝执行并说明可理解的原因 | 改问可访问范围内的问题 |
| 无数据 | 展示空结果及所用条件 | 调整时间/筛选条件 |
| 超时/模型或数据服务失败 | 说明暂时无法完成；不返回生成的假答案 | 重试或缩小范围 |
| 查询被安全策略拦截 | 停止执行；记录内部可审计原因 | 修改问题；不可通过提示词绕过限制 |

## 8. 非功能与质量要求

- **可复现**：相同程序、Mock 数据版本、语义目录版本和查询条件应产生相同的数据结果。
- **可追溯**：可关联原始提问、结构化意图、语义定义版本、查询执行、结果和耗时；敏感密钥不得进入日志。
- **安全**：模型输出和用户输入均视为不可信内容；查询必须由服务端做白名单、只读和范围校验。
- **可迁移**：应用代码通过存储接口访问数据；本地到云迁移后，黄金问题的结果保持一致。
- **可理解**：面向非技术用户解释指标和条件；如展示 SQL，应放在验收/调试入口。
- **性能**：目标响应时长和数据规模待确认；Harness 需分别记录解析/模型、查询和端到端耗时。
- **数据隐私**：全程只使用合成数据；是否向外部模型发送字段描述/样例值在 P4/P7 明确策略。
- **多轮边界**：只继承上一轮明确的指标和时间范围；允许补充或调整一个维度；每轮展示解析结果和查询条件并重新校验；不跨主题、不推断省略信息、不支持复杂分析链。
- **Mock 数据规模**：建议覆盖约 6–12 个月，包含订单、订单明细、商品、类目和渠道等必要关联；具体记录数依照 P3 验收题确定，不预设大规模。

## 9. 验收框架

黄金问题结构已在 P2 建立；P3 已补齐固定指标公式、字段映射、数据版本和精确预期值，见 `docs/acceptance/GOLDEN_QUESTIONS.md`、`docs/acceptance/GOLDEN_RESULTS.md`。不得在口径未定时伪造预期数字。

验收覆盖至少包括：

- 问题类型：单指标汇总、多指标汇总、趋势、排行、分组、周期对比、比例指标、口径解释、歧义澄清。
- 解析内容：指标、维度、时间、筛选、排序/Top N、粒度。
- 结果：指标计算、数据集/Mock 版本、图表与表格一致性、口径/查询条件展示。
- 负例：未知指标、无数据、无关问题、提示注入、越权/危险查询、模型输出不合规、服务失败。

### 建议验收指标（目标值待项目方确认）

| 指标 | 计算方式 | 建议目标/状态 |
|---|---|---|
| 结构化意图准确率 | 黄金集中指标、维度、筛选、时间全部匹配的题数 / 有效题数 | 先建立基线；数值目标待确认 |
| 查询结果正确率 | 结果满足预期查询逻辑和数值容差的题数 / 可执行题数 | 首版确定性路径中所有选定验收题必须通过 |
| 关键负例拦截率 | 危险/越权/未知对象负例正确阻止数 / 关键负例总数 | 所有关键安全负例均须拦截 |
| 澄清正确率 | 正确发现歧义并询问必要信息的题数 / 澄清题数 | 先由黄金集定义，再确认目标 |
| 答案依据完整率 | 展示所需口径与条件的回答数 / 成功回答总数 | Must 用例全部展示 |
| 响应时长 | 分析完整链路与分阶段耗时 | 待目标硬件/模型/数据量确定后确认 |
