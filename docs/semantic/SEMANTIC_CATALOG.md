# 电商业务语义目录（P3 评审稿）

- 目录 ID：`ecommerce_mock_semantics`
- 版本：`0.1.4`
- 首个机器可读迁移版本：`0.1.0`；当前活动版本：`0.1.4`；可直接恢复的已归档版本：`0.1.3`、`0.1.4`
- 对应数据集：`ecommerce_mock_v1`
- 状态：P3 阶段门已核验通过；核心指标、维度、术语、时间规则、澄清策略及固定数据黄金数值均已完成
- 时区：`Asia/Shanghai`

## 1. 目录使用约束

语义目录是问数解析与执行的唯一业务定义来源。首版确定性解析、未来模型解析都只能引用目录中的 ID；不能根据字段名自行推导公式。每次查询记录数据集版本、目录版本和解析出的结构化计划。数据集/目录版本不兼容时拒绝执行。

机器可读的活动配置位于 [`ecommerce_mock_semantics.json`](../../backend/chatbi/catalogs/ecommerce_mock_semantics.json)，由服务启动时严格校验并加载为不可变快照。本文保留人工可读的业务口径；配置和代码中的受控模板共同决定运行时可用语义。

## 2. 指标词典

所有首版金额单位为 CNY，保留两位小数；首版只纳入下列三项。退款率不在首版可执行指标中。

| 指标 ID | 标准名 | 定义 / 公式 | 粒度与时间口径 | 适用维度 | 同义表达 | 状态 |
|---|---|---|---|---|---|---|
| `sales_amount` | 销售额 | 支付成功或已完成的去重订单，其折后实付金额之和；明细/分组时按 `order_items.line_amount_after_discount` 汇总；退款不回写、不扣减 | 订单/明细；按 `paid_at` 上海自然日 | 日期、商品、叶子类目、渠道 | 销售额 | 首版 |
| `order_count` | 订单数 | 符合有效订单条件的去重 `order_id` 数；商品/类目分组仅计含该商品/类目的订单一次 | 订单；按 `paid_at` 上海自然日 | 日期、商品、叶子类目、渠道 | 订单量、成交订单数 | 首版 |
| `average_order_value` | 客单价 | `sales_amount / order_count`；分组后在该组范围重新计算，不对明细 AOV 求平均 | 订单；按 `paid_at` 上海自然日及查询区间 | 日期、叶子类目、渠道；商品维度可用但需明确小样本 | 客单价、平均订单金额 | 首版 |
| `refund_rate` | 退款率 | 暂无首版口径；需另行确定金额率/订单率、部分退款、分母订单 cohort 和退款事件时间 | 待定义 | 待定义 | 退款率 | 后续；拒绝首版执行 |

### 有效订单条件

`order_status IN ('paid','completed') AND paid_at IS NOT NULL`。订单数按 `order_id` 去重；总体一个订单只计一次。取消、未支付、关闭订单不参与三项首版指标。0 元有效订单不生成；可生成未支付、取消等无效订单验证状态过滤。订单支付金额为折扣后、退款前实付金额。例如实付 180 元后退款 30 元，销售额仍为 180 元并计入支付当天。

### 派生比较

- 变化额：`current_value - comparison_value`。
- 变化率：`(current_value - comparison_value) / comparison_value`；比较值为 0 时返回 `null` 并显示“无法计算增长率”，不得返回无穷或 0%。
- 客单价：分组内有效订单数为 0 时返回 `null` 并显示“该时间范围无有效订单”，不得返回 0 元或除以零。
- UQ-09 分解：对用户明确的两个期间，令 `S = O × A`（销售额、订单数、客单价），以旧期为基准：`ΔS = (O₂-O₁)×A₁ + O₂×(A₂-A₁)`。两部分精确加总为销售额变化；解释为数值分解，不声称因果。

## 3. 维度词典

| 维度 ID | 标准名 | 来源 | 值层级/筛选 | 适用规则 |
|---|---|---|---|---|
| `order_date` | 支付日期 | `orders.paid_at` | 上海本地自然日、周、月 | 相对日期必须用固定参考日期及半开区间 |
| `product` | 商品 | `products.product_id` / 名称 | 商品 ID、名称；支持分组、筛选、排序 | 名称别名需唯一；Top N 同值按 `product_id` 升序稳定打破并列 |
| `category` | 类目 | `products.primary_leaf_category_id` → `categories` | 叶子类目 | 每个商品唯一归属一个主要叶子类目；本期仅叶子类目分组；订单是否涉及该类目决定是否计 1 单；订单跨类目时各类目均计一次，因此类目订单数之和可大于总体去重订单数 |
| `channel` | 渠道 | `orders.channel_id` → `channels` | 渠道 ID、标准名 | 每订单唯一渠道；未识别渠道拒答/澄清 |
| `region` | 地区 | `customers.region_code` | 省级合成代码 | 首版非需求范围，不向用户推荐为可执行维度 |

排序默认规则：金额/订单数/客单价降序时，同值按维度规范 ID 升序；Top N 上限建议 20，超过上限提示调整。排序上限需在 SDD/安全策略中落实。

## 4. 术语与别名

| 术语 | 解析目标 | 规则 |
|---|---|---|
| 销售额 | `sales_amount` | 规范名 |
| 成交金额 | `sales_amount` | 建议别名；只有确认其业务口径与支付金额相同时才启用 |
| 订单数、订单量 | `order_count` | 映射为有效订单去重数 |
| 客单价、平均订单金额 | `average_order_value` | 映射为销售额除以去重订单数 |
| 收入 | 无默认映射 | 解释已定义的销售额口径，并询问“收入”具体含义；澄清前不执行查询 |
| 营业额 | `sales_amount` 或需澄清 | 有些语境近似销售额，但未确认前列为歧义词 |
| 退款率 | `refund_rate`（不可执行） | 首版明确告知暂不支持，不返回估算值 |
| 最近 N 天、昨天、本月、本周 | `order_date` 过滤 | 按第 5 节固定时间规则解析；不包含参考日期当天 |

别名匹配优先级：精确规范名 → 已批准别名 → 唯一明确语义匹配 → 澄清/拒绝。大小写/空格/常见标点归一化，不做无边界模糊匹配。冲突词绝不静默挑一个定义。

## 5. 时间规则

- 参考日期由数据集 manifest 的 `as_of_date=2026-08-01` 提供；数据窗口为 `[2025-08-01,2026-08-01)`。
- 时区固定 `Asia/Shanghai`；日期过滤均是 `[start, end)`。
- 昨天：参考日期减一天；最近 N 天：`[as_of_date-N, as_of_date)`。
- 周一为周起始日。“本周/上周”均截至最近一个完整自然日；跨期比较按已完成天数对齐。
- 固定快照中参考日是数据区间的排他结束边界。“本月”定义为最近完整数据日所在月份：2026-08-01 的本月为 2026 年 7 月，上月为完整自然月 2026 年 6 月。一般进行中的月份按当月月初至最近完整日，与上月相同日数范围比较；若上月天数较少，则截到月末。
- 请求参考日期之后的数据返回无数据，不推测、不生成结果。

## 6. 查询计划约束与权限

计划对象最少包含：`metric_ids[]`、`dimension_ids[]`、`time_range`、`filters[]`、`sort`、`limit`、`comparison_period`、`clarification_state`。每个字段必须来自目录允许值。SQL 不接受用户/模型直接执行；服务端将计划编译为只读受控查询。

首版允许数据集内公开的 Mock 指标和维度；禁止写操作、任意字段、系统表、未知指标、超出数据集时间范围的结果推断。涉及未知术语、跨主题、省略关键周期或粒度冲突时先提示/澄清。UQ-04 商品 Top 10、UQ-05 类目汇总、UQ-06 渠道客单价未给时间时，必须先澄清时间范围，不得默认查询完整数据窗口。

## 7. 目录校验规则

1. 每个指标、维度、术语、表字段均有唯一稳定 ID；引用目标存在。
2. 指标定义引用字段与 schema 类型兼容；金额单位、时间字段和过滤条件齐全。
3. 别名归一化后不得指向多个指标；已标为歧义的术语不得配置自动默认映射。
4. 指标所需表之间存在已登记关系，关联基数和去重逻辑明确，防止 join 放大。
5. 关系引用两端字段类型一致；主外键约束和粒度声明完整。
6. 首版问题所需指标/维度均处于 active 状态；后续指标在首版计划中必须拒绝执行。
7. 时间规则包含时区、参考日期、区间闭开性和比较期策略。
8. 目录版本变化时跑所有黄金问题；不兼容更改提升主版本，定义修正提升次版本，文案修订提升补丁版本。

## 8. 已确认口径与规范落实

项目方已确认支付口径/退款处理、类目订单重复计数、固定参考日/数据范围、数据规模/不生成 0 元有效订单、UQ-04–06 缺少时间时先澄清、UQ-09 先澄清比较周期，以及“收入”不映射销售额并在澄清前不查询。本阶段按已完成数据月处理月初快照，并为一般进行中月份规定同期比较算法；规则已同步写入 Mock 数据规范及黄金问题集。

## 9. 目录变更、版本和回滚

1. 修改活动 JSON 前，先把当前已接受版本原样存入 `backend/chatbi/catalogs/releases/ecommerce_mock_semantics_<version>.json`；同时更新活动配置的 `version` 和 `change_note`。已归档版本只用于审阅/回滚，不会被运行时加载。
   变更评审记录使用[目录变更模板](CATALOG_CHANGE_TEMPLATE.md)。
2. 兼容新增别名或术语使用次版本；纯文案修改使用补丁版本；指标定义、能力映射、状态或时间/数据集语义变化使用主版本。增删改动必须能由版本检查工具归类。
3. 在项目根目录运行以下命令，第一条检查活动目录和数据 manifest，第二条比较变更前后的目录契约：

   ```powershell
   & .\.venv\Scripts\python.exe -m backend.chatbi.semantic_catalog
   & .\.venv\Scripts\python.exe -m backend.chatbi.catalog_versioning .\backend\chatbi\catalogs\releases\ecommerce_mock_semantics_0.1.3.json .\backend\chatbi\catalogs\ecommerce_mock_semantics.json
   ```

4. 评审版本差异后运行 `scripts/check.ps1`、P6 HTTP Golden 和 P7 意图 Golden；检查报告显示预期的目录版本后再发布。
5. 回滚时从 `releases/` 中复制指定的已发布 JSON 到活动配置（包括原版本号和 change note），或通过 Git revert 已提交的发布变更恢复完整文件；重新校验目录、运行黄金集并部署。不要只改回版本号而保留新目录内容。当前工作树尚无 Git 提交，因此此刻应使用 `releases/` 快照恢复；正式发布前将活动目录和快照纳入首个受控提交。
6. 服务端会话创建时固定目录 ID/版本。当前快照与会话不匹配时，API 返回 HTTP 409 并要求新建会话、重述问题，不执行旧计划。当前会话存于进程内存，部署重启会清空；后续持久化会话仍须保留版本并继续执行此检查。
